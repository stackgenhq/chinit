# secrets — AWS ClickHouse Cluster

Stores the three ClickHouse user passwords (`default`, `admin`, `writer`) in
AWS Secrets Manager, grants the instance-profile roles read access, and
rotates the passwords on a schedule — built on AWS-native primitives
(Secrets Manager + a rotation Lambda).

## Resources

| Resource | Purpose |
| --- | --- |
| `aws_secretsmanager_secret` ×3 | Password containers (`<cluster_name>-<user>-password`), 7-day recovery window |
| `aws_secretsmanager_secret_version` ×3 | The Terraform-created initial value (user-provided or generated) |
| `aws_secretsmanager_secret_policy` ×3 | GetSecretValue granted ONLY to `allowed_role_arns` (instance roles) |
| `random_password` ×3 | 16-char alphanumeric passwords for null inputs |
| `aws_lambda_function` + role/policy/log-group | The rotation engine (python3.12, `templates/rotation-lambda.tftpl.py` zipped via the archive provider) |
| `aws_lambda_permission` ×3 | Lets Secrets Manager invoke the Lambda, scoped per secret ARN |
| `aws_secretsmanager_secret_rotation` ×3 | Attaches the Lambda + `rate(<rotation_days> days)` schedule to each secret |

### Password generation rules

Passwords are **16 characters, alphanumeric only**. ClickHouse's
`users.xml` stores credentials inside XML elements, so quotes and ampersands
break the XML parser — and would need escaping implemented identically in
cloud-init heredocs AND the rotation Lambda. Alphanumeric eliminates the
whole class of failure in both paths. The same charset is generated by the
rotation Lambda (`string.ascii_letters + string.digits`).

## Rotation flow

AWS only ships **predefined** rotation Lambdas for RDS — there is no native
rotation for custom passwords like ClickHouse's. This module therefore
deploys a small custom Lambda implementing the standard Secrets Manager
four-step protocol:

```
Secrets Manager schedule fires (rate(N days) per secret)
  │
  ├─ createSecret    Lambda generates a new 16-char password and calls
  │                  put_secret_value → stored as AWSPENDING
  │                  (AWSCURRENT keeps serving the old password)
  ├─ setSecret       Lambda calls SSM SendCommand (AWS-RunShellScript) to
  │                  the fleet, tagged NodeType ∈ {writer, reader, backup}:
  │                    • instances run `aws secretsmanager get-secret-value`
  │                      THEMSELVES with their instance role (the password
  │                      never transits the Lambda or its logs)
  │                    • render /etc/clickhouse-server/users.d/
  │                      zz-<user>-password.xml with the new SHA256 hash
  │                    • `systemctl restart clickhouse-server`
  ├─ testSecret      deliberate no-op — the Lambda has no network route to
  │                  ClickHouse; the SSM invocation status IS the signal
  └─ finishSecret    Lambda promotes the pending version to AWSCURRENT
                     (old version moves to AWSPREVIOUS)
```

Details worth knowing:

- **One Lambda, three secrets.** The Lambda maps secret-name suffix →
  ClickHouse user, so a single function + role + log group rotates all
  three secrets, each on its own schedule.
- **`rotate_immediately = false`** — on a fresh cluster the fleet does not
  exist yet; an immediate rotation would dispatch SSM with zero targets,
  fail `setSecret` and strand the secret in AWSPENDING (which blocks all
  later rotations of that secret). The first rotation happens on schedule,
  with the fleet up.
- **users.d merge order**: rotation files are named `zz-<user>-password.xml`
  so they sort AFTER cloud-init's bootstrap `z_users.xml` and win ClickHouse's
  config merge; otherwise the bootstrap hash would silently override every
  rotation.
- **Keepers are not targeted** — they run `clickhouse-keeper`, hold no
  `users.d`, and `systemctl restart clickhouse-server` would error there,
  wedging rotation.
- **Cross-cluster safety** does not rely on the tag: a foreign cluster's
  instance role is absent from the secret policy, so its
  `get-secret-value` fails and the script aborts (`set -e`) before writing
  anything.
- **Terraform vs rotation**: versions created by the Lambda are invisible to
  Terraform (the `aws_secretsmanager_secret_version` resource holds only
  the bootstrap version), so bootstrap and rotation never conflict.

### IAM the Lambda needs

`secretsmanager:Get/PutSecretValue`, `DescribeSecret`,
`UpdateSecretVersionStage` on the three secrets; `ssm:SendCommand` on
`AWS-RunShellScript` + the region's instances; `logs:PutLogEvents` on its
own log group (30-day retention).

## Manual fallback (rotation Lambda failed)

If a rotation wedges (e.g. SSM agent down fleet-wide, or a step failed
mid-flight), nodes can end up rendered with a password that no longer
matches AWSCURRENT. Re-sync every node with the module output — an exact,
paste-ready AWS CLI command:

```sh
tofu output -raw ssm_manual_resync_command
# aws ssm send-command --document-name AWS-RunShellScript \
#   --targets Key=tag:NodeType,Values=writer,reader,backup \
#   --parameters 'commands=["set -euo pipefail ..."]' --region <region>
```

The embedded script pulls all three current (AWSCURRENT) secrets, re-renders
`/etc/clickhouse-server/users.d/zz-<user>-password.xml` with each SHA256
hash, and restarts `clickhouse-server` — the same operations the Lambda
performs in `setSecret`. Because it reads AWSCURRENT (not a pending
version), it is also the recovery path when a secret is stranded in
AWSPENDING: the stuck pending version times out and the current value is
re-applied fleet-wide.

Prerequisites for the fallback: instances run the SSM agent (preinstalled
on the golden AMI and standard Ubuntu AMIs; every node role carries
`AmazonSSMManagedInstanceCore`) and their roles are in `allowed_role_arns`.

## Inputs / Outputs (summary)

- **Inputs**: `cluster_name`, `credentials_config` (null = generate),
  `tls_secret_name_prefix` (documents the ACME module's cert secret naming:
  `<prefix>-tls-certificate/-private-key/-ca-certificate`), `tags`,
  `allowed_role_arns`, `rotation { enabled, rotation_days }`.
- **Outputs**: per-user `*_secret_arn` / `*_secret_name` /
  `*_secret_version_id` (version ids sensitive), aggregate `secret_names` /
  `secret_arns` maps, `rotation_lambda_arn`, `rotation_enabled`,
  `rotation_days`, `ssm_manual_resync_command`.
- **No password values are output.** Plaintext lives in Secrets Manager;
  retrieve it with the instance role or an operator call:
  `aws secretsmanager get-secret-value --secret-id <name> --query SecretString --output text`.
  The root module surfaces a redacted `instructions_to_connect` hint.
